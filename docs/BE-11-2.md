# JARVIS BE 11.2 — PostgreSQL, Flyway, Spring JDBC

## Zakres
- baza `jarvis_db` w lokalnym kontenerze PostgreSQL na 127.0.0.1:5433
- migracja `V1__create_jarvis_tables.sql`
- tabele: `jarvis_conversations`, `jarvis_messages`, `jarvis_training_runs`, `jarvis_model_checkpoints`
- repozytoria JDBC i `ChatPersistenceService`, transakcje Spring
- testy Maven z H2 w trybie PostgreSQL

## Granice odpowiedzialnosci
- **PostgreSQL**: rozmowy, wiadomosci, metadata treningow/checkpointow
- **Dysk**: duze pliki wag/checkpointow
- **LLM runtime**: obliczenia i trening, nie wykonuje SQL
- **Angular**: jeszcze ma lokalny ChatStore; przejscie na backend w BE 11.3/FE 11.4
- **Security**: nie ma nowych endpointow w tym etapie; nigdy nie udostepniaj JDBC browserowi

## Zasady Flyway
- Migracji V1 po zastosowaniu nie edytujemy; kolejne zmiany to V2, V3...
- `spring.flyway.baseline-on-migrate=false` chroni przed automatycznym przyjeciem cudzej schemy
- `spring.sql.init.mode=never`: nie laczymy `schema.sql` i `data.sql` z migracjami
- DB musi istniec i byc dostepna podczas uruchamiania realnej aplikacji

## Testy
Testy H2 dowodza dzialania SQL w trybie zgodnosci, ale nie zastepuja smoke testu prawdziwego PostgreSQL.
W testach Maven konfiguracja w `src/test/resources/application.properties` izoluje testy od `jarvis_db`.

## Bezpieczenstwo
`.env.jarvis` nie dodawaj do repo. Port PostgreSQL publikuje sie tylko na localhost, haslo ustaw sam. W produkcji potrzebny jest inny mechanizm provisioningu DB i zarzadzania sekretami.
